# Property and locality data contract (version 2)

This is the **live input format** used by the website, not a proposed API format.
It replaces the old version-1 documentation-only property template.

## Files to use

| Purpose | File |
| --- | --- |
| One blank property record | `docs/property-input/project.template.json` |
| Current Canopy demo, in the live format | `docs/property-input/project.demo-example.json` |
| One blank locality record, including expanded sections | `docs/locality-input/locality.template.json` |
| Fictional locality example with numeric fields populated | `docs/locality-input/locality.demo-example.json` |
| Published/draft property catalog | `data/properties.json` |
| Published/draft locality catalog | `data/localities.json` |
| Authoritative strict validation rules and TypeScript types | `lib/catalog-schema.ts` |

## Publishing workflow

1. Fill one template object per project/phase and one per locality. Keep the exact
   camelCase keys and nesting. Do not copy the old version-1 snake_case format.
2. Use stable, unique lowercase IDs such as `the-canopy` and `whitefield`. The ID is
   the URL segment. Changing a display name does not require changing its ID.
3. Put locality objects in the array in `data/localities.json`. Put project objects
   in the array in `data/properties.json`. The files are arrays, not `{data: ...}`
   wrappers. Individual template files are objects; the website does not scan them.
4. Set each property's `localityId` to the exact locality `id`. Publish that locality
   before or alongside its properties. Do not match records using locality names.
5. Set `coverImageId`, `primaryConfigurationId` and optional `floorPlanImageId` to IDs
   in that same record. Put assets in `public/images/...`; use `/images/...` in JSON.
   HTTPS image/document URLs are also supported. Supply actual image alt text and rights credits.
6. Remove unused array entries (`[]`) and unknown optional values (`null`). Replace
   all template text/images. Dates are `YYYY-MM-DD`, never guessed day values.
7. Keep `published: false` while preparing data. Set it to `true` after verification.
   Set `isDemo: false` only for genuine records. Both flags are independent.
8. Run `npm run validate:data`, `npm run test:catalog`, and `npm run typecheck`.
   Invalid keys, invalid icons, duplicate IDs and broken relationships are rejected.
9. `npm run dev` reloads changed JSON at **http://127.0.0.1:3000**. Production changes
   require `npm run build` and a restart/redeploy. Both dev/start are pinned to 3000.

There is no upload endpoint, CMS, database, or live scraping service in this change.
Your scraper should output this contract, then merge its records into the two catalog
arrays. `app/data.ts` validates/imports those files and supplies every catalog view.
Draft records are hidden from views, **not secret**: the catalog is bundled client-side.
Never put credentials, private owner contacts, or unpublished sensitive documents here.
Enquiry forms remain preview-only and do not send leads.

## Conventions

- All keys shown in the templates are required structurally; nullable fields accept
  `null`. Unknown keys are rejected to catch misspellings. Empty optional arrays are valid.
- Money is a JSON **integer in INR**, not a formatted string or a crore value.
  `16500000` means INR 1.65 crore. Display formatting is automatic.
- Area is numeric **square feet** and must declare its basis. Distances are km;
  travel times are minutes with a mode. Do not put units inside numeric fields.
- `null` means unknown. Zero is a real value (e.g. a studio has `bedrooms: 0`).
  Prices and areas must be positive when known. Use `null`, not zero, for unknowns.
- Plain text is rendered as text, not HTML. Do not scrape markup into descriptions.
- Arrays preserve their display order. Catalog order is the default recommendation order.
- Missing optional sections are hidden. No prices, areas, nearby distances, metrics,
  amenities or FAQs are generated by the page to fill gaps.
- Sources/dates document provenance; validation does not establish factual accuracy.

## Shared fields

| Key | Type / meaning |
| --- | --- |
| `schemaVersion` | Exactly `2` |
| `id` | Unique slug within properties or localities; letters a-z, digits, single hyphens |
| `published` | Boolean; only true records appear in routes, search and cards |
| `isDemo` | Boolean; distinguishes illustrative data from real inventory |
| `name` | Display name |
| `searchKeywords` | Array of alternate names, abbreviations or useful query terms |
| `coverImageId` | ID of a member of `images` |
| `images` | At least one image; gallery order follows this array |
| `coordinates` | `{ "latitude": 12.97, "longitude": 77.59 }` or null; map link fallback |
| `mapUrl` | HTTPS map link or null; overrides coordinate-generated Google Maps link |
| `faqs` | Array of `{ "question": "...", "answer": "..." }`; empty hides FAQs |
| `sources` | Array of `{ "label": "Developer brochure", "url": null, "checkedAt": null }` |
| `updatedAt` | Last editorial update date or null; shown when supplied |

### Image object

| Key | Type / meaning |
| --- | --- |
| `id` | Unique image slug within this record |
| `src` | `/images/project/cover.webp` or HTTPS image URL; not a filesystem path |
| `alt` | Required accessible description of this specific image |
| `caption` | Visible caption; use an empty string to omit |
| `kind` | `exterior`, `interior`, `amenity`, `floor-plan`, `map`, or `locality` |
| `credit` | Image attribution/rights text, shown in the gallery; empty if inapplicable |

Image paths are case-sensitive when deployed to Linux. Local assets must exist.
External images must allow public browser access; expiring/authenticated URLs are unsuitable.
Gallery count and previous/next navigation adapt to any number of images.

## Property fields

| Key | Meaning / rendering |
| --- | --- |
| `localityId` | Exact locality ID; drives locality page association and filter |
| `type` | `Apartment`, `Villa`, or `Plot` |
| `status` | `Ready to move`, `Under construction`, or `New launch` |
| `developerName`, `phaseName` | String or null; displayed below project title and searched |
| `address`, `postalCode` | String or null; postal code must be six digits; displayed/searched |
| `description` | Main overview paragraph |
| `possession` | `{ "label": "Dec 2028", "date": null }`; exact date only when verified |
| `primaryConfigurationId` | Configuration supplying default detail-page facts and price |
| `configurations` | At least one actual configuration; see below |
| `icons` | Icon keys for `configuration`, `area`, `status`, `possession`, `location` |
| `facts` | Additional counts/specifications: `{ "label": "Towers", "value": 4, "unit": "", "icon": "Building2" }` |
| `highlights` | Icon/text highlights: `{ "icon": "CheckCircle2", "title": "...", "description": "" }` |
| `amenities` | Same shape as highlights; each amenity is explicitly supplied |
| `nearbyPlaces` | Location-panel destinations using the place structure below |
| `documents` | `{ "label": "Project RERA ID", "value": "Verified registration here", "icon": "ShieldCheck", "url": null }`; URL makes value a link |
| `relatedPropertyIds` | Ordered list of other property IDs; `[]` automatically suggests up to three, same locality first |
| `content` | Section copy object; fields below |

`facts[].value` accepts text or a number. For numeric facts the unit is separate.
Use facts for project land area (e.g. acres), units, towers, floors, open-space ratio,
parking or other published project statistics. Use documents for RERA, approvals,
brochure, cost sheet, title-review status and downloadable project documents.
Do not put per-configuration prices/bedrooms in facts: filters read configurations.

### Configuration object

| Key | Type / meaning |
| --- | --- |
| `id` | Unique slug within the project |
| `label` | Visible configuration name, e.g. `3 BHK - Type A` |
| `bedrooms` | Integer 0-30 or null; 0 means studio; plots must use null |
| `bathrooms` | Integer 0-30 or null; plots must use null |
| `areaSqFt` | Positive number or null |
| `areaBasis` | `carpet`, `built-up`, `super-built-up`, `plot`, `unspecified` |
| `startingPriceInr` | Positive integer rupees or null |
| `priceNote` | Inclusions, exclusions, price validity or caveat; empty if unnecessary |
| `availability` | `available`, `limited`, `sold-out`, `on-request` |
| `floorPlanImageId` | Image ID whose kind is `floor-plan`, or null |

If one layout has multiple area/price combinations, provide separate configurations
instead of combining unrelated minimums. Bathrooms and area are shown on the page;
the existing filter interface searches bedrooms, budget, type, status and locality.
Sold-out configurations remain visible in the detail table, but do not match bedroom
or budget filters. Unknown-price configurations appear without a budget restriction;
an active budget restriction excludes them. Unknown values are displayed as on request.

### Section copy (`content`)

`overviewTitle`, `layoutsTitle`, `amenitiesTitle`, `locationTitle`, `documentsTitle`,
and `faqsTitle` are section headings. `layoutsNote`, `amenitiesNote`,
`locationDescription`, and `documentsDescription` are optional visible text (empty
string hides the text). Layout/navigation/button labels and enquiry wording remain
shared UI copy, not property-specific data.

## Locality fields

| Key | Meaning / rendering |
| --- | --- |
| `city`, `state`, `country` | Geographic display metadata; current site is Bengaluru-focused |
| `zone` | Zone label, e.g. `East Bengaluru`; locality index tabs derive from this |
| `tagline` | Hero subtitle and locality index description |
| `description` | Main locality overview |
| `tags` | Short visible traits; also included in related properties' search index |
| `considerations` | Array of practical buyer considerations, shown as paragraphs |
| `highlights` | `{ "icon": "Compass", "title": "Who it may suit", "description": "..." }` |
| `metrics` | `{ "label": "...", "value": 3, "unit": "parks", "icon": "TreePine", "asOf": null, "note": "" }`; value accepts text/number |
| `connectivity` | Transport connections using place objects; Getting around section |
| `nearbyPlaces` | Schools, hospitals, shopping, parks, employment hubs; Everyday essentials |
| `infrastructure` | Development/status objects below; empty hides section |
| `market` | Market object below or null; null hides entire section |

Locality property counts and cards are derived from published projects with matching
`localityId`. Do not maintain a second property-ID array or manually entered listing count.
Locality galleries appear when there is more than one image. These expanded sections
work on desktop and mobile without changing the existing mobile navigation/design.

### Place object (property `nearbyPlaces`, locality `connectivity` / `nearbyPlaces`)

```json
{
  "name": "Verified destination name",
  "category": "Metro",
  "icon": "TrainFront",
  "description": "Route context and relevant caveats.",
  "distanceKm": null,
  "travelMinutes": null,
  "travelMode": null,
  "mapUrl": null
}
```

`travelMode` is `walk`, `drive`, `transit` or null. Distances/times are nonnegative;
times must be whole minutes. Property distances should be from the project entrance;
locality distances should name the reference point in `description`. State how/when
travel times were measured. Avoid presenting estimates as guaranteed commute times.

### Infrastructure object

`{ "title": "...", "icon": "TrainFront", "status": "proposed", "description": "...",
"expectedCompletion": null, "sourceUrl": null }`

Status must be `operational`, `under-construction`, or `proposed`. Completion is an
exact date or null. Use description for a verified month/year when no exact day is known.

### Market object

`{ "summary": "...", "minPricePerSqFtInr": null, "maxPricePerSqFtInr": null,
"rentalYieldPercent": null, "asOf": null, "sourceUrl": null }`

Rates are numeric rupees per square foot, not project prices. The minimum cannot
exceed the maximum. Yield is a percentage (3 means 3%, not 0.03). Supply the sample,
property/area basis and limitations in summary, plus a source and date for actual figures.
The example locality's numbers are explicitly fictional and are NOT live catalog data.

## Icons

Use these case-sensitive Lucide keys. The application maps them to actual icon
components; never provide SVG markup, React code or icon URLs in an `icon` field:

`Building2`, `House`, `LandPlot`, `BedDouble`, `Maximize`, `ShieldCheck`, `Handshake`,
`KeyRound`, `Compass`, `MapPin`, `TreePine`, `Dumbbell`, `Waves`, `Car`, `Users`,
`TrainFront`, `BriefcaseBusiness`, `School`, `Clock`, `CheckCircle2`, `FileText`,
`Hospital`, `ShoppingBag`, `Bath`, `Ruler`.

To add another supported icon, update both `iconNames` in `lib/catalog-schema.ts`
and the explicit map in `components/catalog-content.tsx`. Operational icons such as
save, gallery arrows and search remain shared UI controls.

## Search and filter mapping

- Search: project name, developer, phase, address, postal code, type, status,
  configuration bedroom labels, project keywords, locality name/zone/city/tags/keywords.
  Searches are case/accent insensitive and punctuation-normalized; all query words
  must occur somewhere in the index. This is token matching, not fuzzy/geographic search.
- Locality: exact `localityId`. Locality detail links use `/properties?locality=whitefield`.
- Type/status: exact enum values. Bedrooms: numeric `configurations[].bedrooms`.
- Budget: `configurations[].startingPriceInr`. Bedroom and budget conditions must
  match the **same non-sold-out configuration**. Results show/sort its lowest matching
  starting price and corresponding area/bedrooms, never values from different units.
- Without configuration filters, listing cards use the cheapest non-sold-out
  configuration (falling back to primary for all-sold-out projects). Home/related
  cards and detail-page headline use the designated primary configuration.
- Price sorting puts unknown prices last in both directions. Default search includes
  the entire catalog, not a hardcoded 50-lakh-to-5-crore slice. Slider bounds expand
  to cover supplied prices; no budget is applied until selected or provided by URL.
- URL values `min` and `budget` remain in **crores** for existing UI links, e.g.
  `/properties?min=1&budget=2&bhk=3&locality=whitefield`. JSON uses INR.
- Saved homes use stable property IDs in browser local storage. No personal data
  or saved state belongs in property JSON.

The catalog validator runs automatically on import and manually via `validate:data`.
It does not authenticate external sources, check remote image availability, send
enquiries, create redirects for renamed IDs, or upload records to a server.
