Aaramv Codex Implementation Prompt
Instructions for updating the existing website from the companion master
Open the real website repository in Codex. Attach both Word documents. Ask Codex to read the complete master, including its tables and embedded media. The master is self-contained; the two production photographs can be extracted from its DOCX archive without another download.
How to start
Attach Aaramv_Website_Content_and_Image_Master.docx and this prompt document in the coding task.
Copy the implementation prompt below into Codex, or tell it to execute the prompt from this document.
Keep the actual website source, fonts, assets and repository instructions available. A public URL alone does not provide editable source code.
Use the final checklist to review the local result. Deployment is outside this implementation prompt.
Implementation prompt begins
Task
Update the content and imagery across the existing Aaramv website using Aaramv_Website_Content_and_Image_Master.docx as the consolidated source. Implement the work in the actual repository. Preserve the website's current design identity and component family. This is a complete content and image refinement across the current routes, not a wholesale visual redesign.
Read before editing
Read AGENTS.md and other applicable repository instructions. Inspect the framework, routing, data model, fonts, shared components, image handling, metadata, filters, saved-home behaviour and enquiry flow. Read every paragraph and table in the master; extract text in document order so table cells and status notes are not skipped. Inspect the embedded visual references. Do not stop after making a plan. Complete the authorised local changes and verify them.
Source precedence
Use the master's exact customer-copy fields for wording. Project Overviews in Part 3 supersede older generic introductions. Written copy overrides words inside image boards. The two difference-section references govern that section's composition; numeric responsive rules and actual readable font metrics govern reflow. Earlier page-layout boards are context only. For factual values, a newer approved primary source already in the repository takes precedence over an older research snapshot; record the source and reason. Do not overwrite a supported current fact with an unresolved research lead.
Design boundaries
Keep the actual logo, navigation, current fonts, rounded cards and header, pill search, royal-blue actions, restrained lime accent, mint support surfaces and lavender forms. Reuse existing spacing, radius and colour tokens. Change copy, relevance of imagery, fact hierarchy and small spacing issues within the current layouts. Do not introduce a new brand, generic card system, animation library, page builder, carousel, map planner or new dependency without a concrete repository need. Keep the site recognisable.
Main page implementation
Apply the master to Home, Properties, Localities, About, Contact, Privacy, Terms, shared footer, enquiry components, saved-home states, no-results states and 404. Preserve existing URLs, slugs, saved IDs and external links that remain valid. Do not create parallel duplicate pages. Consolidate repeated early-stage process copy into the existing buying journey. Keep real supported proof; remove fabricated or unsupported metrics, testimonials and portraits. Do not publish blank owner fields or instruction labels.
Project overview implementation
Update all 27 project records by existing slug and aliases. Each Overview must contain the project-specific summary and three or four supplied highlights. Keep the gallery, Layouts, Amenities, Location and FAQs components. Show the selected project, phase or block, configuration and area basis consistently. Do not blend parent township facts with a specific block, row-house and villament plans, or project-wide formats with one resale asking price. Keep Jasper related to its parent El Dorado without duplicating an offer. Distinguish product type, master area, phase area, total homes and available inventory.
Locality implementation
Update all 17 existing locality records from Part 4. Preserve their slugs and generate project links, counts and home types from actual catalogue relationships. Distinguish broad marketing corridors from registered addresses and exact entrances. Use operator-backed landmarks only as route-check destinations. Do not invent travel times, opening dates, neighbourhood prices, appreciation forecasts, rental returns, flood or water assurances or school proximity. Never present planned infrastructure as operating without a fresh authoritative check.
Accuracy and publication gates
Store source URL, source scope, reviewed date and verification state where the data model allows. Developer-published descriptions are not independent inspections. Registration numbers in Part 5 are references until matched to the correct primary certificate; secondary or held references must not become verified badges. A price needs the actual layout or unit, sale type, inclusions and exclusions, cost sheet and quote date. A status is not a possession date and a certificate validity date is not a handover promise. Keep held values in editor metadata or a short unresolved-items file, omit unsupported promotional stats and continue all other work. Never guess missing facts or paste placeholders into the UI.
Image implementation
Extract the original media from the master using the exact archive entry, target filename and SHA256 index. Inspect before use. AR HERO and AR SUPPORT are the only new production photographs. Both are illustrative scenes; retain their live-text captions and alt text. Keep genuine project and locality images only when accurate and appropriately sourced. Do not replace named-project photos, floor plans, maps, staff portraits or reviews with generated imagery. Older image boards are not production assets. Keep source PNGs, generate responsive encodings through the existing image pipeline if appropriate, set dimensions and avoid layout shift. Do not compress legible plans into tiny thumbnails or alter building architecture.
Aaramv difference section
Recreate the selected desktop composition with real HTML text and CSS or inline SVG. Keep the cream surface, navy headline, teal italic phrase, three staggered documents, mint support shape and teal journey connector. The line must continue visibly beyond Booking to Move-in. Keep Still with you. Use the master's latest exact copy, not shorter reference text. Reuse the current enquiry handler. Do not use the whole screenshot as a background or make a second brief form.
Responsive implementation
Retain the same ideas on phones. Use normal document flow and grid or flex layout; do not position text absolutely to match one screenshot. Stack the hero headline and primary action above the contextual photo on narrow screens. Stack both difference ideas and keep their documents, journey labels and booking annotation readable. Body text should remain at least 16px and controls at least 48px. Use one-column project cards, a usable existing filter drawer or accordion, labelled layout rows and the same meaningful facts. Avoid horizontal overflow, clipped labels, hidden CTA collisions and page-level overflow hiding as a fix.
Forms contact and policies
Reuse the existing enquiry path. In preview mode retain the truthful preview notice and do not show delivered success. If a live endpoint is already connected, show success only after confirmed server receipt and handle failure while preserving input. Do not invent a CRM, external recipient, phone, email, office address, response time or service fee. Do not send real test leads. Use preview policy copy only for actual preview behaviour. Hold live-policy operator, processor, retention and contact fields for real business information; do not fabricate legal approval. Omit incomplete team or contact rows and log the operational blocker without stopping other content work.
SEO and accessibility
Apply unique titles and descriptions from the master and known record values. Use actual canonical URLs, one H1 per page, a meaningful heading order, visible keyboard focus and correct image alt text. Keep information selectable and accessible. No invented ratings, reviews, aggregate offers, authorisation claims, coordinates or business contacts in structured data. Do not make content available only through hover or animation.
Verification
Run the repository's relevant build, type and lint checks. Verify all 27 project and 17 locality records map to the correct existing slugs and preserve relationship integrity. Check that shared cards and detail facts use the same approved record. Test filters against the same layout for budget and bedrooms, unknown prices, developer aliases, saved homes and empty states. Render and inspect the main page families at 1440px desktop and 390px phone widths; check 320px and 768px for overflow. Compare the difference section at the same reference width and correct material typography, spacing and artwork mismatches. Check CTA routes and local validation/failure states using a mock or authorised staging setup. Do not claim a check passed if it could not run.
Finish
Persist the changed files in the existing repository and return a concise completion summary: pages and records updated, assets used, checks run, screenshots where supported, source conflicts still held and operational owner inputs needed. Include changed file paths and remaining material risks. Do not deploy or modify the public website as part of this task. Do not ask for approval of routine reversible local edits; complete the authorised implementation first.
Implementation prompt ends
Extracting the media
A DOCX is a ZIP archive. Read word/document.xml and its relationships to locate images. The exact image paths and hashes are listed in Part 8 of the master. Use Python zipfile or the repository's preferred equivalent. Extract only the named image members to a chosen project asset directory; never trust an arbitrary archive path. Match each hash, then give the extracted file its target filename. Do not assume an image index if Word has re-saved the document.
